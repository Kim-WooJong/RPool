# Minimal transfer (experimental, explicit opt-in)

`rpool pool migrate plan POOL --rebalance --minimal-transfer --all-pcs-upgraded --all-pcs-stopped` freezes object destinations and requires all writers, mounts, uploads and migrations on **every PC** stopped. Upgrade every PC first. Do not reconnect old clients: v3 validation and the unknown `relocate-minimal` plan action reject unsupported execution in cooperating clients, but an already deployed old client can still delete an old v2 source directly. Application fences cannot prevent that. No automatic global stop is claimed.

The default remains independent full-copy relocation. Minimal mode creates a new archive ID and v3 manifest, never rewrites legacy source manifests/keys/roots or existing immutable plans. Every shard has an immutable owner, exact address, size and hash bound into the content root and manifest fingerprint. Unchanged shards are full-hash checked and borrowed read-only without uploads; moved shards are read/written (re-encrypted for destination keys) or reconstructed into the new namespace, verified before publication. Fresh manifest replica reads precede switch. Retirement is separate. No hardlink or provider-side copy support is assumed.

Unsupported layout/coding changes are blocked in minimal mode, never hidden full reapply. An unavailable exact destination or source mutation requires replanning. In-place v3 repair is blocked; restore/reconstruction reads remain possible. Use a new independent archive for repairs requiring writes. Existing reprocess independent-replacement checks are unchanged. Incremental mount reuse is not exclusive ownership or permission to mutate borrowed data.

A sticky immutable-object fence is published under each source namespace before borrowing. New clients refuse repair/drain/deletion there; uncertain fence reads fail closed. This initial implementation conservatively keeps the whole borrowed-source folder, including all generations/revisions/pins/pending references. It does **not** report reclaimed source space. Never bypass reference checks or raw-purge protected namespaces. Copy-created receipts only establish new namespaces; borrowed objects are not rollback targets.

`same_storage_preview` (also GUI review) separates current usage, logical target-after-retire, flow bytes, actual whole-object copy amount, physical peak extra, metadata reserve, reservations, free headroom and blocking gaps. Physical peak spends zero source-retirement credit and accumulates every new archive/drive/pack object even when serial. Server copies still allocate whole bytes. Crypt block/header overhead and metadata allowances are conservative, not exact provider billing. Missing bindings/sizes/quotas are blocked, not zero estimates. Legacy plans without a frozen execution contract require a new plan; immutable plans are never rewritten. Unknown full re-encode sizes require a separate supported full-copy workflow.

Fresh quota checks and a shared process-atomic coordinator reserve parallel/archive/drive catch-up writes without releasing unknown-write shadows. No strict guarantee exists against another PC, provider quota lag or external writers. Shadow reconciliation is conservative; a blocked retry may require a new process and fresh object/quota review. Local work and system-temp scratch free space must be known. Preview is not a runtime success proof; these changes have build-only validation, no real-data migration test.

Whole-shard placement cannot promise perfect uniformity; existing 5 percentage-point gap threshold and no-gap-reversal rule remain. Capacity groups can distinguish disks on the same host while failure groups can still identify the shared server outage. Quota/listing timestamps and phase timing are observations, not measured transfer throughput.
