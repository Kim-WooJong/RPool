# ADR-004 — 현재 동기 구조를 보존하는 I/O 경계

- 상태: 확정 (Main Update 1)
- 근거: MASTER_PROMPT §4 ADR-004, §5.4, transport.md §6
- 관련: ADR-005, ADR-006

## 결정

- 현재 Cargo 직접 의존성과 주요 실행 경로는 **동기 I/O + Rayon** 중심이며
  OpenDAL/Tokio 직접 의존성이 없다(E01 확인: `Cargo.toml`에 OpenDAL/Tokio 없음).
- M1의 기본 선택은 **동기·object-safe·streaming StorageBackend 경계**다.
- 기존 GUI와 command 전체를 async로 변환하지 않는다.
- OpenDAL이 요구하는 async runtime / blocking bridge는 **OpenDAL adapter 내부의
  명시적 소유**로 제한한다(ADR-005).

## 결과 (실행 규칙)

- read/write마다 runtime을 새로 만들지 않는다.
- runtime worker 안에서 부적절한 nested `block_on`을 하지 않는다.
- I/O는 **GUI thread에서 수행하지 않는다**(기존 child/background-thread 모델 유지).
- 기존 Rayon worker와 backend 내부 concurrency의 곱으로 요청 수가 폭증하지 않게
  **backend별 bounded concurrency / deadline / cancel 경계**를 설계한다.
- cancellation을 요청했다는 이유만으로 blocked child I/O가 즉시 중단된다고 주장하지 않는다.
- 실행 모델을 바꾸려면 current callers, Send/Sync, runtime lifetime, 취소, backpressure의
  영향을 ADR로 먼저 비교한다.

## 반론/한계

- transport.md §6: Rayon × adapter × rclone retry/concurrency가 곱해질 수 있다.
  → backend registry/service가 **shared per-backend semaphore/budget**를 소유해야 한다.
- subprocess 호출에 explicit deadline이 없어 streaming loop가 child pipe에서 block될 수 있다.
  → `OperationContext`(deadline/cancel)를 transfer/adapter로 전파하고,
  원격 acceptance 후 cancel/timeout은 `UnknownOutcome`으로 표현한다.
- 이 ADR은 "async로 전환한다"가 아니라 "동기를 보존하면서 경계만 둔다"다.
