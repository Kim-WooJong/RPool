# ADR-001 — Archive engine과 미래 filesystem을 구별

- 상태: 확정 (Main Update 1)
- 근거: MASTER_PROMPT §4 ADR-001, §0 범위
- 관련: ADR-002, ADR-003

## 결정

현재 RPool은 **manifest 기반 archive/shard engine**이다.
ObjectId / Generation / VolumeId 같은 type을 추가한다고 해서
filesystem namespace나 distributed transaction이 생기는 것은 아니다.

Main Update 1(M1)의 목표는 **legacy archive engine의 transport coupling 제거**다.
Native Data Layer와 namespace 구현은 Main Update 2로 이월한다.

## 결과

- M1에서 추가하는 `BackendId` / `ObjectKey` / `ObjectRef` / `Generation` /
  `VolumeId` / `TransactionId` / `ShardId`는 **runtime/admin 해석용 type**이다.
- 이 type들은 legacy manifest v1/v2 JSON에 field로 침투하지 않는다
  (compatibility.md §5, ADR-002).
- M1 종료 시 "archive engine이 backend-neutral transport를 사용한다"가 성취 기준이고,
  "filesystem이 되었다"는 성취가 아니다.
- namespace, mount(FUSE/WinFsp/macFUSE), distributed transaction, POSIX 호환은
  M1 범위 밖이다(MASTER_PROMPT §0 "구현하지 않을 것").

## 반론/한계

- type을 도입하면 "이제 filesystem 같다"는 오해를 부를 수 있다.
  문서와 API 명세에서 "archive engine"이라는 표현을 유지한다.
- M2에서 이 type을 namespace/transaction으로 확장할 때, M1에서 만든
  type이 그 계약의 일부가 되는지 재검증해야 한다.
