# ADR-002 — StorageBackend와 MetadataStore 책임 분리

- 상태: 확정 (Main Update 1)
- 근거: MASTER_PROMPT §4 ADR-002, §5, §6 R4
- 관련: ADR-001, ADR-003, ADR-005

## 결정

- `StorageBackend`는 **key에 대한 bytes 접근과 제한된 backend operation**만 제공한다.
  (stat / read / ranged read / write / delete / list / copy / rename)
- `Generation`, `namespace`, `commit visibility`, `lease`, `conflict policy`는
  **MetadataStore / coordinator**의 책임이다.
- 여러 backend의 `write`를 호출하는 것으로 distributed commit을 구현하지 않는다.
- M1에서는 미래 MetadataStore의 **계약과 요구사항만 문서화**한다.
  구현되지 않은 MetadataStore를 "성공하는 stub"으로 등록하지 않는다.
- Local/Memory에서 구현한 CAS는 **해당 구현의 제한된 범위(process-local)**일 뿐,
  cloud multi-client 안전성의 증거가 아니다.

## 결과

- `StorageBackend` trait에는 Manifest / Coding / GUI / namespace transaction을 넣지 않는다.
- `dyn StorageBackend`가 되려면 object-safe(비 generic method)를 유지한다.
- M1의 legacy manifest는 여전히 **authority**다(MASTER_PROMPT §3.1, §10).
- MetadataStore/authority는 ADR-003의 미정 사항이 결정·검증되기 전까지
  M1에서 stub으로 등록하지 않는다.

## 반론/한계

- "CAS를 구현했으니 distributed 안전하다"는 주장은 금지된다.
- Memory/Local CAS가 동작한다고 cloud CAS를 광고하지 않는다.
- M2에서 MetadataStore를 구현할 때 이 ADR의 계약과 ADR-003의 blocking 조건을
  먼저 충족해야 한다.
